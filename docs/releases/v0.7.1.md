# EATF v0.7.1 — malformed ML-DSA entries are rejected, not crashed on

This patch makes both verifiers return `valid: false` instead of crashing on
malformed ML-DSA-65 entries. A malformed `signature_pqc.sig` now gets the same
first-failure code from both verifiers (TypeScript and Python, both built by
Tyche Institute), with or without `--pqc-signer-key`, and so does a malformed
`pqc_public_key.pem` when a key pin is supplied; see [Not changed](#not-changed)
for the unpinned case. In v0.7.0 and earlier, several of these entries crashed
one or both verifiers, and on a few the two verifiers returned different
results.

## Fixed

Starting from the lab's `01-valid-hybrid.aep` (and `04-classical-transition.aep`
for the last row):

| Entry change | TypeScript in v0.7.0 | Python in v0.7.0 | v0.7.1, both |
|---|---|---|---|
| `signature_pqc.sig` is not base64 | crash, exit 2 | traceback, exit 1 | `PQC_SIGNATURE_ENCODING` |
| valid signature with one `!` inserted | crash | accepted | `PQC_SIGNATURE_ENCODING` |
| signature with a BOM or non-breaking space | accepted | traceback | `PQC_SIGNATURE_ENCODING` |
| signature whose base64 length is not a multiple of four | `PQC_SIGNATURE_INVALID` | traceback | `PQC_SIGNATURE_ENCODING` |
| `pqc_public_key.pem` is an RSA key or not PEM | `PQC_VERIFY_ERROR` | traceback without a key pin | `PQC_VERIFY_ERROR` |
| empty `pqc_public_key.pem` | `PQC_VERIFY_ERROR` | `PQC_PAIR_INCOMPLETE` | `PQC_VERIFY_ERROR` |
| empty pair added to a classical-only package | `PQC_VERIFY_ERROR` | accepted | `PQC_VERIFY_ERROR` |

None of these let a forged ML-DSA-65 signature pass `--require-pqc`, or a
signature made by a key other than the pinned one pass `--pqc-signer-key`. The
accepted cases were lenient readings of an authentic signature, or (in
Python) a classical-only reading of an empty pair, which `--require-pqc` and a
pin already rejected. They were still cases where the two verifiers returned
different results for the same package.

## Changes

- New failure code `PQC_SIGNATURE_ENCODING`, with `pqcValid: false`, when
  `signature_pqc.sig` does not decode. It mirrors `RSA_SIGNATURE_ENCODING`.
- One decoding rule for `signature_pqc.sig` in both languages: TAB, LF, VT,
  FF, CR and space may appear anywhere, and the remaining bytes must be base64
  with at most two trailing `=` and a length that is a multiple of four.
  Signatures written by `eatf-sign` are unaffected, including ones re-wrapped
  at 64 columns.
- An ML-DSA entry that exists counts as present even when it is empty, in
  both languages.
- A Python `cryptography` backend without ML-DSA support (OpenSSL older than
  3.5) reports `PQC_SUPPORT_UNAVAILABLE` instead of crashing.
- Check order: pair and policy checks, then the optional key pin
  (`PQC_VERIFY_ERROR` or `PQC_SIGNER_NOT_TRUSTED`, with `pqcValid: null`),
  then the signature encoding, then the signature.

## Not changed

Without a key pin, the two key parsers still disagree on some malformed
spellings of `pqc_public_key.pem` that only one of them can load: for example
the raw 1952-byte key as bare base64 without PEM armour, a raw key under an
arbitrary PEM label, or a valid PEM block followed by other text, which verify
only in Python. With `--pqc-signer-key` both verifiers parse the key by the
same rules. Aligning the unpinned path is planned for a later release.

## Verification

- 31 new tests in each language, built from the lab packages with the same
  cases in both (the signature cases run with and without a key pin), plus 4
  Python-only tests for `PQC_SUPPORT_UNAVAILABLE`.
- Conformance: 5 accepted and 8 rejected vectors in both CLIs, unchanged.
- The deterministic lab replays 42 observations with zero verdict or
  first-failure-code mismatches. Its output is byte-identical to v0.7.0, and
  the conference ZIP has the same contents as the v0.7.0 one.
- The decision-path experiment gives 21/21, unchanged.
- A differential run over 34,522 generated signature and key entries (not
  included in the repository) found no crash and no signature-entry
  disagreement. Without a key pin, 2,591 of its key-entry cases still
  disagree (see [Not changed](#not-changed)).

## Versions

All npm workspaces and the Python package are 0.7.1. `eatf-verify`,
`eatf-sign` and `eatf-inspect --version` report 0.7.1.
