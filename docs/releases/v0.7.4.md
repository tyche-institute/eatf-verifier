# EATF v0.7.4 — an exact legacy RSA check, and one reading of the key, metadata and signature entries

This patch makes the legacy RSA signature check exact. It also has the two
verifiers (TypeScript and Python, both built by Tyche Institute) read
`public_key.pem`, `metadata.json` and the base64 signature entries by one
rule. Abdel Fane (OpenA2A) found the RSA issue with an independent second
verifier built from the documents, and the documentation changes answer his
table of places where that verifier had to guess.

## Fixed

### The legacy DigestInfo path compares the whole block

After a strict RSASSA-PKCS1-v1_5 failure, v0.7.3 and earlier stripped the
padding and compared only the trailing 32 bytes of the recovered block with
the SHA-256 digest. Any bytes between the padding and the digest, any padding
length and any DigestInfo prefix were accepted. The fallback now builds the
one block the Java reference signer produces (full-length padding, a SHA-256
DigestInfo with absent parameters, the digest) and requires the recovered
block to equal it. The report says when this legacy form was used. RFC 8017
Appendix B.1 requires NULL parameters, so writers must not produce it. No
forgery is known against the e = 65537 keys used here; the lenient comparison
is the class of Bleichenbacher 2006 and BERserk 2014.

`valid/valid-overt-profile`, `valid/mcp-tools-call-valid`,
`valid/mcp-tools-call-denied-policy` and `invalid/tampered-overt-receipt` are
re-signed in the RFC 8017 form with the same 2048-bit test key
(`scripts/resign-rsa-signature.py`); only `signature.sig` changed in each.
Strict implementations (OpenSSL 3.0, pyca/cryptography, and Go `crypto/rsa`
in the second verifier) rejected the three valid packages before.
`invalid/tampered-overt-receipt` now fails at the receipt check it is meant
to exercise for those implementations too.

### One reading of the key, metadata and signature entries

- `public_key.pem` must be exactly one PEM block labelled `PUBLIC KEY`, read
  by the PEM rule that `pqc_public_key.pem` already used. Its DER must be the
  SubjectPublicKeyInfo of an RSA key, with nothing after it. Signer pins are
  compared on that DER.
- `metadata.json` must be UTF-8 without a byte order mark, with no member
  name repeated within one object (RFC 8785 Section 3.1), no `NaN` or
  `Infinity` literal, and at most 64 nested objects and arrays. Each of these fails
  with `METADATA_INVALID_JSON`.
- `signature.sig` and `overt_receipt.sig` follow the `signature_pqc.sig`
  base64 rule.

Before, the two verifiers disagreed on some of these inputs. The TypeScript
verifier accepted a byte order mark or invalid UTF-8 in `metadata.json` and
unpadded base64. The Python verifier accepted two PEM blocks, a PKCS#1
`RSA PUBLIC KEY` block and stray bytes inside base64, and rejected `NaN` with
another code. Both kept the
last of two equal member names, which other JSON readers may not.

## Also in this release

- A `timestamp.tsr` that is present but empty or gives no usable token is
  reported as "empty or not a readable RFC 3161 TimeStampResp or token"
  instead of "missing or empty".
- `docs/aep-format.md` now states how entry names are matched, that unlisted
  entries are ignored, the archive limits, the base64 rule, the bytes of the
  step 3 form, the DER comparison in step 5, the signature encoding in
  step 6, that a trailing LF in `hash.sha256` is accepted, and what
  "integer-valued" means.
- `docs/authority-record-v1-scope.md`, the README and the cross-check table
  are corrected. The v0.7.3 text said the RFC 3161 tokens of the frozen
  authority-record corpus bind none of its packages. Each parseable token's
  imprint is in fact the SHA-256 of an RSA signature value: the package's own
  `signature.sig` in 6 vectors, and that of `valid/valid-overt-profile` in
  the other 51. None is over `hash.sha256`, so every verdict, count and class
  in the table is unchanged.

## Not changed

- Conformance verdicts: 5 accepted and 8 rejected vectors in both CLIs.
- `artifacts/authority-record-v1/` and the lab ZIP have the same contents as
  in v0.7.3.

## Verification

- `lib/test/strict-entries.test.ts` and
  `lib-python/tests/test_strict_entries.py` run the same 19 cases in both
  languages; 8 of the TypeScript and 9 of the Python cases fail against the
  code before this change. The new DigestInfo tests in both languages sign
  hand-built blocks with the development key; the four rejection cases fail
  against v0.7.3.
- The v0.7.3 and v0.7.4 Python verifiers give the same verdict on each of the
  1,313 distinct `.aep` files kept on the project's server.
- The deterministic lab replays 42 observations with zero verdict or
  first-failure-code mismatches; the decision-path experiment gives 21/21.
