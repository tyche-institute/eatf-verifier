# EATF v0.7.2 — both verifiers parse packaged ML-DSA-65 keys alike

This patch closes the difference that v0.7.1 listed under "Not changed": without
`--pqc-signer-key`, the two verifiers (TypeScript and Python, both built by
Tyche Institute) now parse a packaged `pqc_public_key.pem` by the same rules.

## Fixed

Without a key pin, starting from the lab's `01-valid-hybrid.aep` with only
`pqc_public_key.pem` changed. These are the spellings in the shared test table:

| Key entry | TypeScript in v0.7.1 | Python in v0.7.1 | v0.7.2, both |
|---|---|---|---|
| an SPKI PEM block followed by a second block | `PQC_VERIFY_ERROR` | accepted | `PQC_VERIFY_ERROR` |
| an SPKI PEM block followed by other text | `PQC_VERIFY_ERROR` | accepted | `PQC_VERIFY_ERROR` |
| the raw key as bare base64 without armour | `PQC_VERIFY_ERROR` | accepted | `PQC_VERIFY_ERROR` |
| the raw key under an unknown PEM label | `PQC_VERIFY_ERROR` | accepted | `PQC_VERIFY_ERROR` |
| a `BEGIN ML-DSA-65 PUBLIC KEY` line closed by `END PUBLIC KEY` | `PQC_VERIFY_ERROR` | accepted | `PQC_VERIFY_ERROR` |
| a trailing NUL, or an END line with a sixth trailing dash | `PQC_VERIFY_ERROR` | accepted | `PQC_VERIFY_ERROR` |
| a legacy raw-key PEM without padding | accepted | `PQC_VERIFY_ERROR` | accepted |
| a legacy raw-key PEM with a leading byte-order mark | accepted | `PQC_VERIFY_ERROR` | accepted |

In v0.7.1, Python read an unpinned key with cryptography's PEM loader (for
text containing `-----BEGIN PUBLIC KEY-----`) or with a non-validating
fallback (for anything else); earlier versions crashed where v0.7.1 returned
`PQC_VERIFY_ERROR`. Python now uses the exact port of the TypeScript PEM
parser that v0.7.0 added for pins, and returns `PQC_VERIFY_ERROR` with
`pqcValid: false` for exactly the key text TypeScript cannot parse. With
`--pqc-signer-key` the two verifiers already parsed the key by the same rules.

Whenever only one verifier accepted a package, that package carried its
authentic ML-DSA-65 signature, and the verifier checked it under the key it
had read. Without a pin neither verifier authenticates the packaged key, so
these differences changed which verifier accepted a package, not what an
acceptance shows. A few cases differed only in the first-failure code.

## Also in this release

- `docs/pqc-hybrid-lab-five-minute-fallback.md` now replays the v0.7.0
  results, with the three policies and a timed row for package 07. The lab
  ZIP has the same contents as in v0.7.0 and v0.7.1.

  PEM block, parsed by the same rules as a pin.

## Verification

- Both test suites assert one shared table of 12 packaged key spellings
  without a pin; 9 of them fail on v0.7.1 Python.
- A differential run over 34,522 generated signature and key entries and
  5,088 PEM spellings (not included in the repository) found no crash and no
  verdict or first-failure-code difference between the two verifiers, with or
  without a key pin. Without a pin, v0.7.1 had 2,591 and 599 such
  differences; with a pin it had none. Every changed Python result moved to
  the TypeScript result.
- Conformance: 5 accepted and 8 rejected vectors in both CLIs, unchanged.
- The deterministic lab replays 42 observations with zero verdict or
  first-failure-code mismatches; the decision-path experiment gives 21/21.
- Remaining cosmetic difference: for a PEM body that is not valid base64 the
  `failureReason` text differs between the verifiers; the failure code and
  `pqcValid` are the same.

## Versions
